# Controller staged workflow

[Repository home](../README.md) · [Orientation](orientation.md) · [Canonical status](https://github.com/motion-tennis/documentation/blob/main/docs/project-status.md) · [Shared stages](https://github.com/motion-tennis/documentation/blob/main/docs/project-stages.md) · [Task and handoff template](https://github.com/motion-tennis/documentation/blob/main/docs/contribution-workflow.md)

This table maps shared stage IDs to controller work. The central status is the only authority for the active stage; this file adds no parallel schedule or automatic progression. Each contribution names one stage and bounded slice, expected evidence, allowed files and deferred work. A local exit check supports the shared gate but does not advance it on its own.

| Stage | Scoped controller deliverable | Verifiable exit evidence | Explicitly deferred work |
| --- | --- | --- | --- |
| **S0 — Shared contract/coordination baseline** | Review controller responsibilities, versioned doubles/roster contract dependencies, profile compatibility and fixture/acceptance plans; clarify MPU-6050/Zephyr/INT evidence gaps; add small contract/codec validation tools only when explicitly tasked | Recorded contract decisions and cross-owner dependencies; generated-codec compatibility/size/resource fixture results for the tasked contract slice; documentation checks and status recorded centrally | Firmware/runtime codec integration, board drivers, live networking and the complete game; contract-validation fixtures are not runtime implementation |
| **S1 — Isolated minimal component slices and fixtures** | A separately authorized local Zephyr/MPU-6050 capture slice with verified 200 Hz configuration, original IDs/times and safe default-off/bounded outputs; local fixtures for that slice | Pinned board/toolchain configuration and real build instructions; filter/divider readback, observed cadence/loss and safe-output evidence for available hardware; synthetic evidence labeled | WLAN/session integration, battery/marker/clock feasibility campaigns, real Pi/game path and full gameplay |
| **S2 — Feasibility and transport** | Bounded WLAN/session transport, battery/power observations and shared-INT hardware-marker probes; stubs support early isolated checks, then actual Pi/controller clock-exchange and mapping probes with fake pose/game as needed | Real Pi/controller drift, uncertainty, asymmetry and restart evidence; reproducible manifests, transaction accounting, link/power results, shared-INT/timestamp uncertainty and marker loss/overlap records; stub-only results do not pass the hardware gate | A playable game, real end-to-end acceptance, four-player scoring and the matched full A/B campaign |
| **S3 — One-controller integrated diagnostic transaction** | One controller with real tracking, Pi clock maps/uncertainty, required ball request/response, atomic commit, matching feedback and explicit marker links | One complete correlated trace plus hit/miss/error/timeout cases; local `t0`/`tr`/eligible `t1`, map versions and electrical evidence; no missing mandatory state exchange | Four-player match claims, AI filling, automatic expansion to scoring/serve work not needed by this diagnostic slice |
| **S4 — Four-controller 2v2 playable game** | Four confirmed bindings and continuous body-relative racket gestures for lift/toss/overhead serving and normal match feedback; Pi independently moves avatar roots automatically under the reviewed extended contract | Four-player readiness, stable identities through side/role changes, all 800 offered sample transactions/s accounted for, and shared gameplay fixtures with Pi/game/tracking owners | Matched external-AP/Pi-hotspot acceptance campaign, performance guarantees, production packaging and true 3D |
| **S5 — Matched topology, load, fault and timing validation** | Controlled external-AP versus Pi-hotspot trials with identical controller stream, marker settings, power policy and declared workloads | Shared test-matrix run bundles, repeated baselines, complete late/failure distributions, uncertainty/clock evidence, battery and radio records; failures not filtered away | Silent rate/threshold changes to make results pass, unmeasured guarantees, unrelated hardware migration and true 3D |
| **S6 — Reproducible demonstrator** | Pin the validated controller firmware/configuration, wiring/power references and build/flash/run/diagnostic procedure | Another contributor reproduces the declared setup/results from saved revisions and manifests; remaining limitations and recovery procedure documented | Unapproved sensor/radio replacements, expanded gameplay and the deferred extension stage |
| **S7 — Deferred true 3D/alternatives** | Only an explicitly authorized experiment for a changed tracking/sensor/radio profile and its controller implications | Separate proposal/profile, compatibility review and measured evidence for the named experiment | Automatic entry after S6, silent replacement of the accepted prototype, or wholesale implementation of every alternative |

For each task, use the shared [contribution workflow](https://github.com/motion-tennis/documentation/blob/main/docs/contribution-workflow.md) to record the baseline revision/status, dependencies, acceptance evidence and handoff. A human can explicitly request a named later-stage slice; record it as a bounded exception and identify missing prerequisite evidence. It neither advances the global stage nor authorizes adjacent future features. Routine fixes within that scope do not need repeated approval.

If central status is unavailable, use a pinned verified status/revision supplied with the task and report the limitation. Do not infer runtime authorization from this table. Stop after the bounded deliverable and its checks; leave the next proposed slice in the handoff instead of beginning it automatically.
